0 · 结论速览 (TL;DR)

正确性 — 通过
融合 op 是语义完全一致的 drop-in：前向输出 + 全部梯度（d_input / d_fc1_w / d_fc2_w / d_prob）对高精度参考 n_fail = 0。输入/输出/ctx 与未融合 [GroupedLinear→SwiGLU→GroupedLinear] 一致。
性能 — 空卡上融合 kernel 真的赢（1.55×）
在正确生产 shape（H=2048, I=512）+ 真正空闲 GPU 上（稳定复现 ×3，0.2369 ms）：融合 DIRECT kernel 652.6 TFLOP/s，比最快的非融合 graph-safe cuBLAS 13.4（422）快 1.55×、比 CUTLASS F0（369）快 1.77×。手写 2-SM tcgen05 kernel 强 compute-bound、对频率极敏感，整机共享限频时（412）把它的优势全吃掉了，空卡才显出来。
真正的瓶颈 = op 封装开销,不是 kernel
早期得到的 0.57× 是双重假象：① GPU 被限频（掩盖了 kernel 对频率敏感的优势）；② 当时测的是 forward_fused_moe.py 这个 op,不是 kernel。空卡上 kernel(652) vs op(397) 显示 op 封装带来 ~39% / 0.15ms 开销(fuser_forward 的 Python marshalling),把集成路径拖到与 cuBLAS 持平。这是该优化的真问题,且是 Python 层、不是 kernel。

3 · 三种 Grouped-GEMM 后端

TE 的 GroupedLinear 在不同条件下走三条完全不同的 grouped-GEMM 路径，性能差别巨大，是理解结论的关键：

后端机制CUDA Graph 可捕获开关
legacy cuBLAS host 端按 expert 循环、逐个发 cuBLAS、multi-stream；m_splits 读回 CPU ✗ 默认 module 路径 / NVTE_USE_CUTLASS_GROUPED_GEMM=0
CUTLASS F0 单个 CUTLASS SM100 Ptr-Array grouped kernel（本项目 F0 也实现的那条） ✓ NVTE_USE_CUTLASS_GROUPED_GEMM=1
graph-safe cuBLAS 13.4 cuBLAS 13.3+ device-side grouped GEMM，m_splits 作为 device tensor，单 kernel 读 device offset ✓ SM100+bf16 默认（ops 路径） / NVTE_GROUPED_LINEAR_USE_FUSED_GROUPED_GEMM=1

「graph-safe」= 把每个 expert 的 token 数（m_splits）放在 device 上、单 kernel 内读 device offset 完成，host 不需知道分段、不做 CPU↔GPU 同步 → 同一张捕获好的 CUDA Graph 对任意 split 值都成立，可被图捕获。MoE 训练里每个 step 路由出的 per-expert token 数都在变，只有 graph-safe 的 grouped GEMM 才能把整段 MoE capture 进一张图来摊薄 launch 开销 —— 这也是 TE 在新 cuBLAS 上默认走它的原因。

4.3 决定性数字 — kernel vs op vs 最佳非融合

融合 kernel 真的最快
空卡上手写融合 DIRECT kernel = 652 TFLOP/s，比最佳非融合 graph-safe cuBLAS 13.4（422）快 1.55×。op 封装（forward_fused_moe.py）= 397，即 ~39% / 0.15ms 的 Python marshalling 开销吃掉了 kernel 的优势，把集成路径拉回到与 cuBLAS 持平（0.94×）。kernel 没问题；要优化的是 op 封装。

5 · 根因分析（已纠正）

  • 融合 kernel 是真赢家。 空卡 652 TFLOP/s，比 graph-safe cuBLAS 13.4（422）快 1.55×。route#2「双 TMEM 累加器 + 融合 SwiGLU epilogue、不物化 [M,2I]」的设计在不限频时确实有效 —— 省下的中间显存写读 + 单 pass 是净收益。
  • 限频是第一个陷阱。 手写 2-SM tcgen05 kernel 强 compute-bound、对 GPU 频率极敏感：共享卡限频时只有 412，空卡 652（+58%）；而 cuBLAS/CUTLASS grouped GEMM 几乎不随频率变（368→370）。所以必须在空卡上比，否则会得出相反结论。
  • op 封装开销是第二个陷阱、也是当前真正要修的点。 空卡上 kernel 直调 652 vs forward_fused_moe.py 397 —— op 层 ~39% / 0.15ms 的 Python marshalling（fuser_forward 里 split→m_tile_expert、prob、FC2 GroupedTensor 构造、ctx 保存等）把 kernel 的优势吃掉，使集成路径退回与 cuBLAS 持平。
  • 之前 0.57× / 2.2× 都是假象： 0.57× = 限频 + 测 op；2.2× = shape 写反（d=512/I=2048）+ 旧 cuBLAS 13.1 基线。正确做法 = 正确 shape（H=2048/I=512）+ 空卡 + 直调 kernel → 1.55×。
  • 对反向（B1 融合 dH）的推论： 既然前向 kernel 能赢 grouped GEMM 后端，融合反向同样有戏（同样省中间显存 + 单 pass）—— B1 值得做，前提是同样把 op 开销控制住。

7 · 结论与建议

结论（已纠正）
在真实生产 shape（H=2048/I=512）+ cuBLAS 13.4 + 空卡下，SonicMoE 前向融合 kernel 真的赢 —— 比最佳非融合（graph-safe cuBLAS 13.4）快 1.55×，且是正确 drop-in（全梯度 n_fail=0）。当前唯一拦路的是 op 封装（forward_fused_moe.py）~39% 的 Python 开销，把集成路径拖到与 cuBLAS 持平。kernel 已验证有效，要做的是把 op 开销榨掉。

建议下一步（按性价比）

  1. 优化 op 封装开销（最高优先）。 profile forward_fused_moe.py::fuser_forward，定位那 0.15ms：很可能是 split→m_tile_expert 的 CPU↔GPU 同步、FC2 GroupedTensor 构造、prob/ctx 处理里的冗余。目标是让集成路径吃到 kernel 的 1.55×。
  2. 做 B1 融合反向（dH-overlap）。 前向 kernel 既然赢，融合反向同样有净收益（省中间显存 + 单 pass）；这是端到端再加速的最大杠杆（当前反向是逐 op 回退）。
  3. 补全空卡 perf sweep。 不同 G / Me（负载不均）、不同 batch；并在空卡上重测 e2e（限频会得出相反结论）。
  4. 继续推进其余 SonicMoE 项：F1 gather on-GPU、F3 combine、F4 router、Memory。
