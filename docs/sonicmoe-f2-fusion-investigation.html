SonicMoE F2 融合前向 — 集成与性能调研报告

把手写 CUTLASS「up-proj GEMM + SwiGLU」融合 kernel 接入 Transformer Engine（NVTE_USE_FUSED_MOE），在生产对齐环境下验证正确性并评测性能。

0 · 结论速览 (TL;DR)

正确性 — 通过
融合 op 是语义完全一致的 drop-in：前向输出 + 全部梯度（d_input / d_fc1_w / d_fc2_w / d_prob）对高精度参考 n_fail = 0。输入/输出/ctx 与未融合 [GroupedLinear→SwiGLU→GroupedLinear] 一致。
性能 — 不及现代 grouped-GEMM 后端
在正确的生产 shape（H=2048, I=512）下，融合前向 0.57×（比未融合慢约 2×）。原因有二，缺一不可：① 之前用错 shape（d/I 写反，用了 d=512/I=2048）；② 之前的基线是旧的慢路径（cuBLAS 13.1 multi-stream）。换到新的 cuBLAS 13.4 graph-safe grouped GEMM 或 CUTLASS F0 grouped GEMM，手写融合 kernel 都打不过。
根因
F0 的 CUTLASS grouped GEMM 本身很好（529 TFLOP/s，与 cuBLAS 13.4 基本持平）。问题出在 F2 的融合方式：route#2 的「双 TMEM 累加器 gate/up + 重 SwiGLU epilogue」设计带来的开销 大于它省下的中间显存写读 —— 融合后 GEMM 反而比纯 F0 慢 ~1.8×。即 F0 grouped GEMM + 单独 SwiGLU > 融合 kernel。

1.2 环境（生产对齐）

TE 2.17 在 SM100+bf16 上，GroupedLinear 默认走 graph-safe grouped GEMM，编译期要求 cuBLAS ≥ 13.3。可用的 NGC 镜像里 25.10=cuBLAS 13.1、26.02=13.2.1 都太旧（GroupedLinear 整个跑不起来）。最终拉取并重建到 nvcr.io/nvidia/pytorch:26.05-py3（CUDA 13.2 / cuBLAS 13.4.1 / torch 2.12 / py3.12），容器 sonic-moe-2605，TE editable 安装在 /data1/min.yang/te_build。所有性能数为该机实测，但整机共享、被其它租户限频，故绝对 TFLOP/s 偏低，相对比值才是结论。

3 · 三种 Grouped-GEMM 后端

TE 的 GroupedLinear 在不同条件下走三条完全不同的 grouped-GEMM 路径，性能差别巨大，是理解结论的关键：

后端机制CUDA Graph 可捕获开关
legacy cuBLAS host 端按 expert 循环、逐个发 cuBLAS、multi-stream；m_splits 读回 CPU ✗ 默认 module 路径 / NVTE_USE_CUTLASS_GROUPED_GEMM=0
CUTLASS F0 单个 CUTLASS SM100 Ptr-Array grouped kernel（本项目 F0 也实现的那条） ✓ NVTE_USE_CUTLASS_GROUPED_GEMM=1
graph-safe cuBLAS 13.4 cuBLAS 13.3+ device-side grouped GEMM，m_splits 作为 device tensor，单 kernel 读 device offset ✓ SM100+bf16 默认（ops 路径） / NVTE_GROUPED_LINEAR_USE_FUSED_GROUPED_GEMM=1

「graph-safe」= 把每个 expert 的 token 数（m_splits）放在 device 上、单 kernel 内读 device offset 完成，host 不需知道分段、不做 CPU↔GPU 同步 → 同一张捕获好的 CUDA Graph 对任意 split 值都成立，可被图捕获。MoE 训练里每个 step 路由出的 per-expert token 数都在变，只有 graph-safe 的 grouped GEMM 才能把整段 MoE capture 进一张图来摊薄 launch 开销 —— 这也是 TE 在新 cuBLAS 上默认走它的原因。

4.3 决定性数字 — 融合 kernel vs 纯 GEMM

融合反而更慢
手写融合 up-proj+SwiGLU 仅 294 TFLOP/s（0.350 ms），而 CUTLASS F0 仅 GEMM（不含 SwiGLU）就 529 TFLOP/s（0.195 ms）。即融合 kernel 比「同样 CUTLASS、却连 SwiGLU 都没融」的纯 GEMM 还慢 ~1.8×。给 F0 再加一个独立 SwiGLU（轻量 elementwise，~0.05 ms）仍然完胜融合 kernel。

5 · 根因分析

  • F0（CUTLASS grouped GEMM）是好 kernel。 529 / 267 TFLOP/s，与 cuBLAS 13.4 持平，远超 legacy multi-stream。F0 这条线本身有价值。
  • F2（融合）才是问题所在。 route#2 的「双 TMEM 累加器（gate col0 / up colN）+ 重 SwiGLU epilogue（TMEM→reg→silu·mul→TMA-store）」设计，把单纯 GEMM 的 529 拖到 294 —— 融合 epilogue 的开销 > 省下的 [M,2I] 中间显存写读。这是「为融合而融合」的反例。
  • 之前 2.2× 的来历是双重假象： ① shape 写反（d=512/I=2048，更利于手写 kernel 的 N 大、K 小排布）；② 基线是旧的 cuBLAS 13.1 merged/2-GEMM 慢路径。两者一改，优势全部消失。
  • 对反向（B1 融合 dH）的推论： 若前向 GEMM 都打不过 grouped GEMM 后端，反向同样会撞 cuBLAS/CUTLASS 这堵墙 —— B1 大概率也赢不了。

7 · 结论与建议

结论
在真实生产 shape + cuBLAS 13.4 环境下，SonicMoE 前向融合（F2）站不住：集成是正确的 drop-in，但对吞吐是 ~2× 的回退。更好的积木是 F0 CUTLASS grouped GEMM（或 cuBLAS 13.4）+ 一个轻量独立 SwiGLU。

建议下一步（按性价比）

  1. 保留并打磨 F0 CUTLASS grouped GEMM（529 TFLOP/s 已与 vendor 持平），作为可被 CUDA Graph 捕获的 grouped-GEMM 后端；不再追前向融合的吞吐。
  2. 若仍要 F2，用 NCU 定位融合 epilogue 为何这么贵（对比 fused vs F0 的 SM/MIO/TMEM 占用），判断是否能把双累加器/epilogue 开销压到低于显存节省 —— 但 vendor 已在 529，空间小。
  3. 显存角度：融合 kernel 唯一仍站得住的价值是不物化 [M,2I] 中间激活，对 activation-memory bound 的训练有意义（不是吞吐）。如要主推此点，应去测激活显存下降而非 TFLOP/s。
  4. 把 SonicMoE 精力转向 grouped-GEMM 后端尚未覆盖、或 vendor 较弱的环节（如特定 FP8/FP4 配方、in-kernel dispatch/combine 的 EP 路径）。
